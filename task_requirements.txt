# Task.pdf summary and implementation plan

I analyzed `TASK.pdf`. The goal is to build a Python HTTP service for HR questions and leave management, tested against a **modified corpus and database**. The safest approach is to implement and test the five requirements in order, while keeping access control and business rules deterministic—not delegated to the LLM.

## What MUST, SHOULD, and MAY mean

- **MUST**: required for the assessment.
- **SHOULD**: expected; if you skip it, explain why in the README.
- **MAY**: optional.
- If an assumption is necessary, record it in the README.
- Correctness and depth matter more than breadth. The five must-pass checks should take priority over optional features.

## The five requirements

### 1. Ingestion and retrieval — start here

**You must:**
- Automatically ingest every file format in `corpus/`, using `manifest.json` metadata. This includes tables and the scanned document; manually transcribing corpus facts is prohibited.
- Keep document metadata with retrieved text: `doc_id`, type, region, effective date, access level, and a citation locator (nearest heading or page).
- Cite every document used, and no unused or inaccessible documents.
- Limit each LLM call to **3,000 corpus-text tokens**, counted with `tiktoken`’s `cl100k_base`; log that count for every call.
- Keep corpus facts out of system prompts.

**Implementation outline:** Build loaders for PDF, DOCX, Markdown, and HTML; extract tables and run local OCR for scanned pages. Chunk and index the extracted content with its metadata. Enforce the token limit when assembling each model context.

**Done when:** Ingestion works automatically on the provided corpus, citations point to the source, OCR/table content is searchable, and tests verify token counting and corpus changes.

### 2. Decide which documents apply

For each question, determine a **reference date**: today from `APP_TODAY`, unless the user asks about a past date.

**Eligibility rules:**
1. The requester’s database-backed role can read the document.
2. The document is for their region or `GLOBAL`.
3. Its effective date is on or before the reference date.

**Precedence when eligible documents conflict:**
1. Authority: policy, addendum, memo, handbook, and calendar outrank FAQ and wiki.
2. Scope: a region-specific document outranks a global document.
3. Recency: a later effective date outranks an earlier one.
4. If still tied, show both values, cite both documents, and say they conflict—do not choose.

**Also account for:**
- A readable upcoming document that would win once effective **SHOULD** be mentioned with its effective date and citation.
- If nothing eligible answers the question, use `no_answer`; if only part is answered, answer that part and identify what is missing.

**Done when:** Tests cover each precedence level, unresolved ties, past-date questions, regional filtering, and upcoming changes.

### 3. Tools and leave rules

Implement these **exact tool names and argument names**:

- `get_leave_balance(employee_id, leave_type?)`
- `list_leave_requests(employee_id, status?)`
- `get_team_leave(start_date, end_date)`
- `apply_leave(leave_type, start_date, end_date)`
- `cancel_leave(request_id)`

Permission checks must happen inside the tool implementation and use the authenticated employee ID from the request header—not the LLM’s claims or chosen identity argument.

**Applying leave:**
- Require `annual` or `sick`; ask if the type is missing.
- Dates are inclusive, within 2026, `start_date` is today or later, and `end_date >= start_date`.
- Count weekdays excluding public holidays from the applicable holiday-calendar document.
- Reject zero working days, insufficient balance, or overlap with the requester’s pending/approved requests.
- On acceptance, create an unguessable request ID, store working days, and subtract the balance in **one transaction**.

**Cancelling leave:**
- Only pending or approved requests with a start date after today can be cancelled.
- Mark cancelled and restore the working days in **one transaction**.

Tools return the current balance only; do not silently add future accrual. Rejections need a specific reason and tool-call status `error`.

**Done when:** Tests cover working days, holidays, date boundaries, balances, overlaps, transactions, cancellation, and role permissions.

### 4. Identity, access control, and personal data

- `X-Employee-Id` and the employee database record are the only source of identity, role, and region.
- Bind each session to the employee who sent its first message; a different employee reusing that session gets HTTP 403.
- Filter documents the requester cannot read **before retrieval results reach the LLM**. Never reveal that restricted documents exist.
- Follow the role matrix for viewing leave data. Refuse bulk employee-data requests; use the same fixed refusal for unauthorized employee IDs whether or not they exist.
- Logs must not contain names, email addresses, or phone numbers. Never show phone numbers; mask email addresses; show names only when the requester is allowed to see them. Send only necessary personal data to the LLM.
- Treat instructions inside documents as untrusted content. Do not let them trigger tools. Refuse prompt-injection or hidden-data requests with route `refuse`.

The README/DESIGN documentation must explain how personal data is protected.

**Done when:** Tests prove that restricted documents never reach the model and unauthorized users cannot see leave data or personal information.

### 5. Conversation behavior

Every response must use exactly one route: `rag`, `tool`, `hybrid`, `clarify`, `no_answer`, or `refuse`. The route determines whether citations and tool calls are empty or populated; follow the response contract exactly.

**Write actions require confirmation:**
1. Validate the proposed action. If invalid, explain why and return a tool error without proposing it.
2. Otherwise, summarize the action and ask for confirmation. Set `pending_confirmation`; do not change the database.
3. Execute only after clear confirmation in the same session, and re-check because data may have changed.
4. Keep at most one pending proposal per session. A changed request creates a new proposal; any other next message discards the old proposal. Never bypass confirmation.

For clarification, ask for **all** missing details in one message. Resolve date phrases consistently: weeks start Monday, “next week” means that following Monday–Friday, and “next Friday” is the first Friday after today. Ask when a date is ambiguous or has passed.

**Done when:** Integration tests cover the routes, response shape, clarification, confirmation/cancellation flow, date interpretation, and refusals.

## Suggested one-by-one work order

1. **Set up the service contract:** FastAPI app, Pydantic request/response models, configuration, session state, and health endpoint.
2. **Complete Requirement 1:** automated loaders, OCR/table extraction, metadata-aware chunks, retrieval, citations, and token accounting.
3. **Complete Requirement 2:** deterministic eligibility and precedence logic around retrieval.
4. **Complete Requirement 3:** the five tools, authorization, leave calculations, and transactional database operations.
5. **Complete Requirement 4:** identity/session binding, document and leave-data enforcement, and PII controls.
6. **Complete Requirement 5:** route selection, clarification, and confirmed write-action state.
7. **Package and verify:** Docker, Compose, tests, README, and DESIGN.md; then test with a modified corpus/database.

## How your preferred technologies fit

- **FastAPI + Pydantic:** Use for the API, validation, and response schemas.
- **LlamaIndex:** A reasonable option for document readers, chunking, and retrieval. Keep eligibility, precedence, authorization, and citations under explicit application control.
- **LangGraph:** Optional for conversation and confirmation state. It must not be the authority for permissions or database rules.
- **DSPy:** Optional for structured LLM tasks. It is not necessary to satisfy the requirements; keep core decisions deterministic and validate model outputs.

You do not need to use every framework. A small, well-tested system is preferable to adding framework complexity.

## Deliverables and acceptance checks

The repository must include `Dockerfile`, `docker-compose.yml`, `.env.example`, tests runnable with `make test`, `README.md`, and a `DESIGN.md` of at most two pages. Compose must mount `./data`, start the service on port 8000, and make `/health` return 200 within 10 minutes after ingestion. Requests must finish within 30 seconds; use the specified HTTP errors for invalid bodies, missing/unknown employee IDs, and session-owner mismatch.

The review stops if any must-pass check fails: Compose/health readiness, restricted-document leakage, unauthorized leave-data access, exceeding the 3,000-token corpus limit, or failure to reflect modified corpus values.
